## 1. Executive Summary & Core Finding

During earlier device testing on the Xiaomi Redmi 9 Power, the user observed an application storage consumption of approximately **76.x MB**. Following a subsequent application update, the displayed storage size in Android Settings dropped to approximately **17.x MB**.

### Core Finding
**No functionality, assets, or native binaries were dropped.** The base APK has remained consistently **~17.1 – 17.6 MB** across every single build in project history. The observed ~59 MB difference was caused by **Android ART's Ahead-Of-Time (AOT) DEX compilation cache (`dex2oat`)**:

1. **Uncompressed Bytecode Physics:** LearnMate AI contains **55.09 MB of uncompressed Dalvik Executable bytecode** across 11 DEX files (`classes.dex` to `classes11.dex`) representing the Jetpack Compose BOM, Material 3, Room DB, Kotlin Coroutines, and AndroidX framework libraries. When packaged in the base APK with ZIP DEFLATE compression, this bytecode compresses to **15.93 MB**, resulting in a base APK of **17.22 MB**.
2. **Android ART AOT Compilation (`dexopt`):** When an app is executed or when the Android background optimization daemon runs, `dex2oat` pre-compiles the Dalvik bytecode into native ARM64 machine code (`.odex`) and a verified bytecode archive (`.vdex`). On the Redmi 9 Power, this compilation generates **56,911 KB (55.57 MB) of `base.vdex`** and **208 KB of `base.odex`**.
3. **Android Storage Accounting:** In Android 12, the Settings app displays:
   $$\text{App Size} = \text{Base APK Size (17.22 MB)} + \text{ODEX/VDEX Compiled Code (55.78 MB)} \approx \mathbf{73.00\text{ MB} - 76.x\text{ MB}}$$
4. **The Update Wipe Mechanism:** When an application is updated via `adb install -r` (`pm install -r`), the Android Package Manager replaces the base APK and **wipes the existing ART compiled code cache**. Right after installation, the Dexopt state is reset to:
   $$\texttt{[status=run-from-apk] [reason=unknown] odex file size: null (0 KB)}$$
   Consequently, Android Settings immediately displays only the raw base APK: **~17.2 MB**.

In addition to resolving this storage accounting question, this investigation identified and fixed a missing JNI packaging configuration: `libexecutorch_llama_jni.so` was compiled and bundled into `app/src/main/jniLibs/arm64-v8a/` without introducing artificial bloat.

## 4. Native Binary Packaging Audit

### Standalone Executables vs. JNI Shared Libraries
In Phase 3.4 / Gate 2, two native executables were compiled:
1. `model/native/arm64-v8a/llama_main` (11.4 MB stripped): Standalone C++ LLM runner containing full TikToken BPE tokenizer, XNNPACK backend, sampler, and mmap loader.
2. `model/native/arm64-v8a/executor_runner` (9.8 MB stripped): General ExecuTorch program runner.

**Architectural Role:**
These binaries are **standalone command-line executables** compiled specifically for isolated, direct ADB execution in `/data/local/tmp/llama_main`. In Android, an APK packages **shared libraries (`.so`)**, not CLI executables with `main()` entrypoints. Packaging `llama_main` inside the APK would violate Android packaging standards and add redundant bloat.

### JNI Shared Library (`libexecutorch_llama_jni.so`)
In Phase 3.3, a native C++ JNI bridge was authored:
- Source: `app/src/main/cpp/native_llama_bridge.cpp`
- Header/Interface: `NativeLlamaBridge.kt` (`System.loadLibrary("executorch_llama_jni")`)

**The Packaging Issue:**
`android-app/app/build.gradle.kts` did not configure an `externalNativeBuild` block. Consequently, Gradle never invoked CMake, and `libexecutorch_llama_jni.so` was omitted from the APK. `NativeLlamaBridge.kt` caught the `UnsatisfiedLinkError` at runtime and safely activated the deterministic offline knowledge base fallback without crashing.

**The Fix Implemented:**
Using Android NDK r26c Clang (`aarch64-linux-android26-clang++`) with `-static-libstdc++`, `native_llama_bridge.cpp` was compiled directly into:
```
android-app/app/src/main/jniLibs/arm64-v8a/libexecutorch_llama_jni.so
```
- **Size:** 357 KB (stripped).
- **Dynamic Linker Dependencies (`readelf -d`):**
  - `liblog.so`
  - `libandroid.so`
  - `libm.so`
  - `libdl.so`
  - `libc.so`
- All dependencies are standard Android Bionic system libraries.

## 7. Conclusions & Architectural Guidelines

1. **The 76.x MB vs 17.x MB discrepancy is an artifact of Android ART's compilation lifecycle, not an APK size regression.**
   - Fresh install = ~17.2 – 17.6 MB.
   - Post-AOT dexopt compilation = ~73 – 76.x MB.
2. **Do not inflate the APK.** Artificially adding 59 MB of dummy data or uncompressed binaries would result in an installed size of ~135 MB once compiled by ART.
3. **In-process JNI inference will cleanly use `libexecutorch_llama_jni.so` (357 KB),** while CLI benchmarking continues to use `llama_main` (11.4 MB) in `/data/local/tmp/`.
4. **Model weights (~3.55 GB `.pte`) remain strictly external** in `/sdcard/Download/` or `/data/local/tmp/llama/` to prevent memory exhaustion and comply with Android installation limits.
